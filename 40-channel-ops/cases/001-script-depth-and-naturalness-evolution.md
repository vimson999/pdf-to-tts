# Case 001 — 从“快速问题驱动”到“问题驱动的研报深读”

> 来源：S01E01《China Trade: Strong surplus, uneven growth support》
> 状态：第一版决策案例
> 目的：记录一次有代表性的脚本方法演进，解释当前视频结构规则为什么会变成现在这样。

## 1. 初始目标

S01E01 的核心问题已经成立：

> 中国出口与贸易顺差表现很强，但为什么对实际产出、就业、收入和国内吸收的传导并不均衡？

最初写作时，我们担心视频退化成“照着 PDF 念”，因此优先强调：

```text
问题驱动
→ 快速抛矛盾
→ 快速给核心数据
→ 快速解释机制
→ 回收结论
```

这个方向解决了“机械摘要”的问题，但也引出了新的问题。

## 2. V2 暴露的问题：压缩过度

V2 的主要问题不是事实错误，而是信息组织太赶。

具体表现：

- 很多数字只承担“证明一句话”的作用；
- 关键图表和结构变化没有真正展开；
- 观众很快听到结论，但没有经历研报本身的推理过程；
- 整体更像“用研报支持一个观点”，而不是“带观众读懂这份研报”。

触发修正的核心反馈是：

> 如果不讲细节、不讲这篇研报本身，那视频到底在讲什么？

这个反馈把问题从“如何避免念研报”改成了：

> **如何把研报讲细，但又不枯燥。**

## 3. 外部样本验证：参考频道为什么长但不拖

随后加入多条参考频道完整脚本样本，覆盖：

- 宏观路演；
- AI 与就业 / 财富；
- 房地产；
- 地方财政；
- 汇率；
- 税负；
- 公司研报。

样本显示，参考频道并不回避“过研报”。它的稳定做法是：

```text
先说这是什么报告
→ 为什么值得看
→ 先给核心结论 / 地图
→ 真正进入研报
→ 关键数据 / 图表处停下来
→ 解释其经济含义
→ 加历史、横向对比、简单计算或个人判断
→ 做小结
→ 回到研报继续
```

因此得到第一次方法修正：

> **结论前置，不等于论证压缩。**

以及：

> **细节不是负担；有解释价值的细节本身就是故事支点。**

由此根方法从“问题驱动”升级为：

> **问题驱动的研报深读。**

## 4. V3 修正：让观众经历证据链

V3 不再只保留：

```text
出口 +25%
→ 高科技集中
→ 就业收入外溢弱
```

而是让观众完整经历：

```text
贸易总量
→ 地区结构
→ 产品结构
→ 高科技与低端消费品分化
→ 价格 vs 数量
→ 实际产出 / 就业 / 收入
→ 进口结构与 final demand
→ 国内吸收
→ 固投、基建、制造业与财政执行
→ 外部缓冲风险
```

并明确识别几个需要“停下来讲透”的节点：

- 出口 +25% 到底由谁贡献；
- 高科技 +56.9%、机械电子 +32.8%、低端消费品 +8.5% 为什么重要；
- 价格驱动和数量增长为什么对经济传导不同；
- 进口 +28.2% 为什么不能直接等于最终需求全面复苏；
- 为什么一篇贸易报告最后会落到国内吸收、固定资产投资和财政执行。

## 5. V3 仍然暴露的问题：头尾太“平”

正文采用平铺直叙、讲逻辑、讲数据的方式是合适的。

但如果开头和结尾也完全使用相同语气，会出现另一个问题：

> 内容正确，但缺少一点节目感。

最初的开头类似：

> 今天想和大家一起看一篇摩根大通刚刚发布的中国贸易研报……

它没有问题，但进入方式偏“上课”。

随后尝试增强技巧时，又发现另一个风险：

> 如果每句话都追求反转、悬念、金句和强过渡，会产生明显的 AI 感和刻意感。

因此第二次方法修正不是“多用技巧”，而是控制技巧密度。

## 6. 最终形成的开头逻辑

当前更认可的开头结构是：

```text
自然打招呼
→ 交代报告与标题
→ 给出一组最值得看的数据
→ 建立正常直觉
→ 轻轻指出报告里的真实矛盾
→ 抛出母问题
→ 带观众进入正文
```

其中一个被认可的尺度是：

> 先正常说话，等真实矛盾出现以后，再轻轻推一下。

例如“这就有意思了”这种轻度节奏词可以保留，因为它只是帮助观众意识到矛盾，而不是人为制造高潮。

## 7. 最终形成的结尾逻辑

结尾不应只是重复正文，也不需要刻意升华。

更适合完成三件事：

```text
回扣开头的大数字 / 母问题
→ 把整篇研报压缩成一个可复用判断框架
→ 留下一句有记忆点但不过度用力的结论
```

当前更认可的表达方向是：

> 以后看到出口创新高，不只问“涨了多少”，还要问：谁在涨、靠价格还是数量、最后能传多远。

相比单纯的“出口强，不等于传导强”，更有节目收束感的版本是：

> **这一轮中国出口的问题，不是强不强，而是这种强，究竟能传多远。**

## 8. 从这次案例提炼出的规则

### Rule / Hypothesis A：正文低技巧密度

正文的主要任务是：

- 把关键数据讲清楚；
- 把图表讲清楚；
- 把机构逻辑讲清楚；
- 把重要细节和结构变化讲透。

不要每隔一小段就强行加入“真正关键的是”“更可怕的是”“问题来了”等模板化刺激。

### Rule / Hypothesis B：头尾允许轻设计

```text
开头：用真实认知缺口拉人
正文：用信息和解释留人
结尾：用判断框架和一句回收让人记住
```

技巧应服务于理解，而不是制造虚假刺激。

### Rule / Hypothesis C：自然表达优先

如果一句话虽然更“像爆款”，但明显不像一个真正读完研报的人自然会说的话，优先选择自然版本。

### Rule / Hypothesis D：不要追求句句是金句

真正的专业感来自：

> 证据扎实 + 解释清楚 + 关键位置有节奏。

而不是全文保持高强度文案腔。

## 9. 仍待验证的部分

这次得到的是方法层面的强观察，还不是完全由频道真实数据验证过的稳定 Rule。

发布后需要重点观察：

- 开头 30 秒留存；
- 关键图表展开时的留存变化；
- 平均观看时长；
- 平均观看百分比；
- 评论是否认为“讲得细但不拖”；
- 观众是否能复述最终判断框架。

如果真实数据与当前判断冲突，应继续修正，而不是因为已经写进 Case 就固化。

## 10. 对知识库结构的启示

这次案例也验证了为什么需要单独的 `cases/`：

```text
methods  = 最终当前规则
episodes = 当集执行过程
cases    = 规则为什么会从 A 变成 B
```

最终规则很重要，但规则是怎么长出来的，同样是知识资产。
