# Cases

这里存放频道方法论演进中的**决策案例**。

Cases 不是单集流水账，也不是最终规则本身，而是记录：

> **一个方法为什么会被提出、被质疑、被修正，最后又为什么形成现在的版本。**

## 与其他目录的区别

```text
methods/   = 现在我们相信什么
episodes/  = 某一集具体做了什么
batches/   = 上游资料批次与候选输入
cases/     = 我们是怎么从分歧、失败和验证中长出方法的
```

## 什么情况值得建立 Case

不是每次讨论都建 Case。只有出现以下情况之一时才值得沉淀：

- 原有方法被真实执行暴露出明显问题；
- 用户反馈与现有方法发生冲突，并推动方法修正；
- 参考样本、数据或发布结果推翻了原假设；
- 同一个问题经历了至少两轮明显版本演进；
- 某个决定未来很可能被重新争论，值得保留依据；
- 最终形成了可跨多集复用的方法规则。

## 推荐结构

每个 Case 尽量回答：

```text
1. 初始目标是什么
2. 第一版为什么这样做
3. 实际暴露了什么问题
4. 触发修正的反馈 / 证据是什么
5. 中间经历了哪些版本
6. 最终采用了什么方案
7. 为什么采用
8. 提炼出哪些可复用规则
9. 哪些规则仍需真实发布数据验证
```

## 记录原则

- 记录**可解释的决策过程**，不保存模型内部思维链；
- 可以记录版本差异、用户反馈、外部样本、实验数据与结论；
- 不机械保存整段聊天记录；
- 不把第三方完整脚本或受限制资料原文复制进公开仓库；
- Case 可以引用 episode 和 method 文件作为上下文；
- Case 本身不自动升级为 Rule，仍需按 `methods/90-knowledge-promotion.md` 判断。

## 命名

建议：

```text
001-<主题>.md
002-<主题>.md
003-<主题>.md
```

编号按创建顺序递增，不按 episode 编号绑定。
